# Paper-трекинг кандидатов (2026-11-05)

Форвардная проверка четырёх кандидатов без сигналов в Telegram и без
изменений live-конфига. Запущен 05.11.2026, крутится в `start_all.ps1`
вместе с ботами; watchdog поднимает процесс при падении.

## Что отслеживается

| Кандидат | Правило | Откуда |
|---|---|---|
| `range_usdcad_atr12` | USDCAD range, `stop_atr=1.2`, ER 0.20, TP 3 | этап 1, главный кандидат |
| `classic_xau_real_yield` | classic XAU без лонгов, когда DFII10 вырос за 20 наблюдений | этапы 1 и 4 |
| `classic_xau_m5` | classic XAU на M5, те же live-параметры, без real-yield фильтра | скальпинг-проверка 05.11.2026 |
| `dual_momentum_idx` | rank 12M по SPX/NDX/DAX/N225, top-1 при 12M>0, иначе cash | этап 3 |
| `tsmom_idx_long` | long-only TSMOM 12M по тем же индексам, месячный ребаланс | этап 3 |

## Как устроено

- `shadow.py step` пересчитывает кандидатов по истории и делает upsert в
  SQLite `shadow.db` (ключ candidate+id). Повторный запуск и пропуск шага
  ничего не ломают.
- `shadow.py loop` — шаг каждые 5 минут; `shadow.py report` — сводка.
- Состояние: `shadow.db` (в `.gitignore`), лог: `logs/shadow.log`.
- Внешние ряды (Yahoo/FRED) обновляются `refresh_external.ps1`: start_all
  запускает его не чаще раза в 7 дней, ошибки снимают штамп и повторяют
  попытку.
- Никаких `tg.send_message`, `post_signal`, записей в `trades.jsonl` и
  изменений `.env`/`start_all.ps1` для live-ботов.

## Отчёт

```
python shadow.py report
```

Показывает два блока: сделочные кандидаты в R и месячные в процентах.
**`ист.`** — история до старта трекинга, **`фв.`** — только записи после
05.11.2026. Смешивать их нельзя: baseline нужен для контекста, решение
принимается по форварду. В колонке «текущая» — позиция по последнему
закрытому месяцу.

### classic_xau_m5: почему paper, а не live

Classic на M5 — единственная скальпинг-схема, которая после издержек осталась
в плюсе на истории: native +20.6R за ~14 месяцев (218 сделок, PF 1.18,
maxDD 16R, t 0.92), Exness +10.8R (PF 1.08). Но:

- t-stat ниже 1: статистически это не доказанный эдж;
- при двойном спреде Exness результат −2.9R (PF 0.98);
- задержка входа на бар ломает схему (на Exness −53R; частично артефакт
  пересчёта риска, но чувствительность реальная);
- в окне последних 180 дней кандидат даёт −0.34R.

Поэтому он добавлен только в paper-трекинг с spread 0.19 и без real-yield
фильтра. Для перевода в отдельный live-инстанс (`BOT_TF=5`) нужно:
30+ закрытых форвардных сделок, net > +3R, PF > 1.1, maxDD < 10R, плюс
положительный повторный прогон на Exness и устойчивость к задержке входа.

## Правила решения (после 3 месяцев)

1. **Сделочные:** минимум 10 закрытых форвардных сделок, `net > 0`,
   `avg_R > +0.05`, просадка не хуже baseline×1.2. Сравнение с live-ботом
   на том же символе за тот же период обязательно.
2. **Месячные:** минимум 3 форвардных месяца, суммарно положительно;
   dual momentum сравнивается с buy&hold SPX за тот же период.
3. Кандидат, который хуже live/бенчмарка или нарушил просадку, уходит в
   rejected и останавливается. Кандидат, который лучше — идёт в обсуждение
   live, но не переключается автоматически.
4. Параметры кандидатов не меняются во время трекинга. Любая правка
   обнуляет форвардную историю и начинается заново.

## Обслуживание

```bash
python shadow.py step      # разовый пересчёт
python shadow.py report    # сводка
python shadow.py loop      # цикл (запускается shadow.bat loop)
powershell -File refresh_external.ps1   # принудительное обновление рядов
```

Остановить: закрыть процесс `shadow.py` (watchdog не должен поднимать его,
если убрать секцию 3.5 из `start_all.ps1`). Перезапуск: `shadow.bat loop`
или обычный `start_all.ps1`.

## Ограничения

- Paper-трекинг использует те же барные модели, что бэктест: без
  проскальзывания сверх спреда, без реального исполнения и свопов.
- Незакрытая сделка помечается `open` на последнем баре; её R — текущая
  переоценка, а не реализованный результат.
- Месячные кандидаты зависят от Yahoo/FRED: если обновление не прошло,
  форвардные месяцы не добавляются (в логе будет `errors>0`).
- `range_usdcad_atr12` и `classic_xau_real_yield` пересчитывают последние
  180 дней; более старые записи в отчёт не попадают.
